Verified safeguards

  • Hosted-function source is implemented. deployment/netlify/functions/upload.mjs uses a server-only handler with explicit credentials, exact HTTPS application origin and the intended Supabase project. It returns 503 unless deliberately configured/enabled. No fixture imports or local fallback exist in the deployment entry. A separate candidate TOML describes function bundling and routing; it is not active.
  • Browser preparation is not trusted. Files over 4 MB and within the existing 8 MiB selection limit are prepared in the browser. A generated 5.9 MB PNG was successfully reduced below the transport limit. The function independently counts streamed bytes, rejects requests above 4,000,000 bytes (below Netlify's effective ~4.5 MB binary limit), validates authenticated ownership through existing RPCs and decodes the actual image bytes.
  • Trusted compression remains mandatory. JPEG, PNG and WebP still images only; 25 MP decode guard; EXIF removed; image maximum 1600 px and 450 KB, thumbnail maximum 400 px and 50 KB. Complex images reduce dimensions/quality; unsupported or uncompressible files fail. Only these optimized outputs enter the private bucket.
  • Only the worker finalizes. Ordinary users cannot write directly to Storage or call privileged finalization. Finalization rechecks current ownership and membership. Wrong-origin, invalid bearer, cross-family destinations, spoofed content, malformed bytes and oversized requests are rejected. Partial-write failure removes the newly written image; a failed deletion keeps capacity reserved for cleanup.
  • Quota reservations now survive content deletion. A new private database ledger closes the cancellation/in-flight race. Its records are inaccessible to browser roles. Concurrent requests across different accounts cannot take the last available slot twice. The 50 MB account cap, 20 daily reservations, global 800 MB cap and 500 KB finalization limit remain.

Evidence: 11 hosted-handler/local-database scenarios, large-file browser transport, 6 quota checks. The function bundle was built locally with server dependencies external. The native Sharp package must be installed for Linux by the future hosting build; this Windows run cannot validate that deployment binary.

What happens at 800 MB

The budget is 800,000,000 bytes (decimal MB), not 800 MiB. A request must fit another 500,000-byte reservation in addition to recorded storage bytes and outstanding reservations. It can therefore stop slightly before exactly 800 MB. Pending uploads may temporarily be double-counted while their stored objects exist but finalization is unfinished; this is deliberately conservative.

  1. Reservation fails before decoding or writing a new object. The hosted handler returns HTTP 429 with Photo storage is nearly full. New uploads are paused until space is available. The existing upload UI displays that error.
  2. Existing photos are neither modified nor deleted. Authorized downloads still succeed; unauthorized downloads still fail. Family records, messages, text posts and sign-in are not disabled by this photo-specific cap.
  3. In-flight uploads with valid reservations can finish. Deleting their parent content cannot release the reserved space early; finalization then fails authorization and the new objects are cleaned up.
  4. Capacity can return after actual orphan bytes are removed, or a canceled reservation expires after one day. Deleting a photo in the UI revokes access immediately but may not reclaim stored bytes until maintenance runs. The current local maintenance runs hourly and processes at most 500 orphan paths per batch; hosted maintenance remains unconfigured.
  5. A local full-capacity test preserved reads, created no new storage object, and resumed uploads after synthetic capacity was freed. No real hosted storage was filled.

The cap protects the application workflow, not a compromised service-role key or manual administrator upload. It is project-local and includes all its recorded Storage objects; it does not cap other projects in the billing organization. Unknown or malformed object-size metadata now pauses new reservations rather than treating those bytes as zero. Provider ingestion/accounting lag still requires dashboard reconciliation. No claim of absolute provider billing enforcement is made.

Validated assumptions and revised estimates

Measured 8 local fixture portraits: combined outputs 14-152 KB, average about 61 KB, with local processing roughly 0.10-0.36 seconds. These are small fixture images, not a production distribution or serverless benchmark. Keep a conservative 180 KB average, a 500 KB worst-case bound, and a provisional 1 GB-second worker allowance per upload until measured on the selected runtime.

Baseline: 20% of registered accounts monthly active; 2 photos/active user/month; 12 months accumulated content; profile photos for 40% of registered accounts. Bandwidth: 120 photo views/active user/month, 70% at 20 KB thumbnails and 30% at 180 KB full images, plus 3 MB API/chat traffic: 11.16 MB per MAU/month. Static app: 4 sessions/MAU/month, 2 MB and 20 requests/session. Emails: 2 per MAU plus new registrations equal to 5% of registered accounts; retries and onboarding bursts are extra.

Database planning: 70 MB baseline +20 KB/account +103 KB/MAU/month for 50 messages, 2 posts, 4 comments and related/index overhead. Local fixture rows average about 81-133 bytes before indexes; small-table physical sizes substantially exceed raw rows. The planning allowances are deliberately higher, but family size, duplicate profiles, long text, indexes and vacuum bloat are not validated at 10,000 users. The database estimate is a planning range, not a capacity proof.

Commercial operation and free-tier constraints

Netlify explicitly allows commercial projects on Free. No blanket noncommercial-only restriction was identified for Supabase or Resend in the reviewed pricing/terms; this is a scoped review, not a guarantee about every future business activity or negotiated account agreement. Resend requires a verified sending domain for arbitrary recipients; test-sender restrictions would prevent real-user authentication. Anti-spam/abuse requirements apply, and usage limits are not permission to send unsolicited email.

Practical barriers remain: Free database/storage quotas, inactivity pausing, no automatic Supabase backup entitlement, provider service suspension/fair-use rules, daily email caps, Netlify account-wide credit exhaustion, lack of an SLA, and unverified restoration. These can interrupt a commercial app even without generating a bill. Do not evade quotas with duplicate accounts or weaken privacy/backups to remain free.

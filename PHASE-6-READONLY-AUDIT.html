Security blockers

  1. Invitation visibility: invites_select_for_authenticated_users permits SELECT TO authenticated USING (true), and table grants include SELECT. It does not isolate invitation fields, including the token column, by recipient/network. Actual values were not read; token hashing/storage format remains unverified.
  2. Membership authorization: memberships_insert_self checks only user_id = auth.uid(). The role constraint allows admin/contributor/viewer and authenticated has INSERT. There is no family approval, valid invitation, or restricted-role check, nor a custom public trigger enforcing one. This is an admin self-assignment and unauthorized enrollment risk; no production exploit was attempted.
  3. RLS recursion: membership SELECT/UPDATE policies query family_memberships itself. Reproduce possible recursion errors locally with fictional users. Accidental query failure is not a substitute for authorization.
  4. Broad grants: anon and authenticated have broad DML plus TRUNCATE, REFERENCES, TRIGGER and MAINTAIN privileges on all three tables. RLS does not cover every PostgreSQL operation. Review least privilege and direct-role exposure; no destructive validation was attempted.
  5. Unverified claiming/relationships: target_person_id has no person-table foreign key. No public person table, verified parentage model, claim workflow, consent model, minor protections or provisional/confirmed relationship separation is present to validate.

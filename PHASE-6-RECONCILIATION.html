Why neither existing schema is sufficient

The repository duplicates ancestry in mother/father columns, names, and generic relationships; permission flags live on client-associated profiles. Its missing initial tables prevent a reproducible build. Hosted tables lack people, parentage, verified relationships and claims. Its unrestricted invitation SELECT, self-enrollment/admin-role gap, recursive membership policies and broad grants are unsafe foundations. Exact findings and catalog procedure are in the read-only audit.

The current engine requires stable person IDs, biological/adoptive parentage and canonical partnership pairs. Preserve that contract through a database-to-graph adapter. Do not replace graph discovery, automatic layout, mobile branch navigation or printable templates.

Proposed normalized baseline

Use a dedicated familyconnect application schema, initially not exposed through the Data API. Keep identity/contact/verification material private. Define a small audited API surface, explicit object grants and RLS; schema separation alone is not authorization. All DDL, policies, grants, functions, tests, configuration and fictional seeds are version-controlled. Keep legacy migrations as history outside the new local migration chain rather than editing their meaning.

Relationship and onboarding behavior

Personal invitation → minimal identity confirmation → immediate supported connection reveal → optional builder → voluntary invitations. Persist an opaque invitation continuation safely through Auth; do not put raw tokens in long-lived client storage or telemetry. If verified edges do not establish a relationship, say so and offer one optional clarification. The clarification creates a proposal, not invented ancestry.

Full/half siblings and cousin terminology are derived from confirmed parentage and known completeness, not stored as competing truths. Unknown parentage cannot establish a full/half classification. A reported sibling with unknown parents stays a provisional assertion. Step connections follow confirmed partnership/parentage context or a separately reviewed social assertion; never convert them to biological edges. The existing engine supports biological/adoptive parentage and partnership paths; do not feed unsupported edge types into it.

Only authorized confirmed edges enter the verified relationship solver. Pending edges can appear distinctly in the builder preview. Resolve approved person equivalences in the request-specific graph projection to avoid duplicate people; deduplicate edges and check cycles after resolution. Preserve original record provenance. A connected network must not reveal hidden intermediate people, or claim a path unsupported by the viewer's authorized data. Network connections do not create new biological relationships.

Implementation choice and migration sequence

  1. Now: review this proposal. No schema-dependent migrations are applied.
  2. After local-only approval: start the unlinked local Supabase workspace, create the new reproducible baseline, seed fictional users/networks and test invitation/claim/review/consent flows. Explicitly ensure app configuration targets localhost; existing .env still targets hosted Supabase.
  3. Test anonymous, unrelated member, contributor, admin and guardian access; token replay/concurrency; duplicate claims; cross-network isolation; cycle and duplicate prevention; exports and existing engine regressions. Measure onboarding time and inspect actual mobile/desktop evidence.
  4. Later, separate hosted approval: inventory backups and all current accounts/configuration; re-count records and inspect any changes. Introduce the reviewed application schema additively in the existing project, preserving auth.users and identities. Design import/mapping only if legacy family rows now exist; do not guess mappings.
  5. Explicitly remediate legacy public grants/policies under the same later approved security plan. Merely adding a secure schema leaves vulnerable legacy API objects exposed. Keep legacy objects/data intact until dependency review and a separately approved retirement decision.
  6. Stage application cutover behind a feature flag. Never run the incomplete old migration chain against production or rebuild the hosted project to get a clean slate.

Risks and rollback

Main risks: unknown external consumers of public tables; unrecorded schema provenance; membership escalation; claim hijacking; private data leaked through connected-network paths; races in token use/cycle checks; Auth redirect errors; and migration grants exposing private objects. A clean local baseline avoids importing those defects but still needs adversarial permission tests.

Before hosted changes, verify actual backup/PITR availability and perform a supported isolated restore rehearsal. Preserve schema, grants, Auth configuration and account continuity; Storage objects require separate recovery if later present. Do not repair cli_login_postgres privileges to obtain a backup. No backup or restore has been performed in this assessment.

Prefer additive expand/contract changes and application feature-flag rollback. On failure, disable new writes and revert application routing while preserving newly collected records; do not drop the new schema or restore a whole database casually, which could erase new Auth accounts or sessions. Keep versioned reverse/forward-fix scripts and old grants for comparison, but do not restore known-insecure permissions as a rollback. No old production onboarding flow is assumed safe.
